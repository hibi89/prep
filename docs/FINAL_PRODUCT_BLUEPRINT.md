# PREP — FINAL PRODUCT BLUEPRINT v1.0
**기준일:** 2026-11-12 KST  
**설계 상태:** 제품 전체 목표 설계(DESIGN BASELINE). 소유자 최종 검수 및 구현 검증 이전이며, 현재 동작/완성/출시를 뜻하지 않는다.  
**공개 주의:** 이 문서는 공개 가능한 추상 설계만 담는다. 비공개 원본 코드·기밀 구조·고객 데이터는 포함하지 않는다.

## 0. 제품 정의와 성공 조건
PREP(Universal Data Preparation Engine)는 사용자가 허가한 **로컬 정형 데이터**를 받아, 결정론적인 규칙으로 **안전한 수집 → 구조 진단 → 명시적 매핑 → 정규화 → 품질 검증 → 검토 대기 → 근거·보고서 생성**까지 수행하는 **독립형 데이터 전처리 제품**이다.

PREP는 고객이 사용할 수 있는 독립 CLI/SDK 형태로 납품되고, 다른 앱이 고정된 버전을 불러 사용할 수 있어야 한다. 100%의 의미는 문서/데모 존재가 아니라 요구 기능 전체 + 실제 패키지 + 플랫폼 테스트 + 승인된 소비자 앱 1곳 연결 + 보안/권리 확인 + 소유자 검수 완료다.

**핵심 가치**
- 동일 입력 + 동일 설정 + 동일 PREP 버전이면 동일한 의미적 출력과 검토 상태.
- 오류·모호함·누락·원본 출처를 **숨기지 않고 검토 큐로 분리**.
- 원본 불변, 기본 외부 전송 0, 필수 유료 API 0.
- 다른 제품의 매출/재무/문서검색 등 업무 규칙을 PREP 코어에 넣지 않음.
- 개인정보/라이선스 권한에 대한 판단은 사용 고객 및 소비자 앱의 권한 관리와 분리.

## 1. 사용자·배포 형태·시나리오
대상: 단독 개발자, 1인 사업자, 내부 분석 담당자, 기업 AX/자동화 개발자. 소비자 제품: 검증된 인터페이스로 PREP를 호출하는 사내 자동화, AI 분석 및 표준화 제품.

### 1A. 로컬 사용자의 완결된 작업 흐름
1. 파일 또는 허용된 로컬 경로를 **명시적으로** 선택한다.
2. PREP가 포맷·인코딩·크기·행/열 수·구조와 위험 요소를 사전 검사한다.
3. 열/타입/필수값을 제안하더라도 **자동 확정하지 않고**, 사용자 설정으로 명시적으로 확정한다.
4. 읽기 전용 dry-run에서 정규화 미리보기, 정상/검토/거부 건수, 검토 사유를 확인한다.
5. 명시적 저장 요청 시 새 경로로 결과와 검증 영수증을 기록한다(덮어쓰기 기본 거부).
6. 사용자나 호출 앱이 검토 큐를 해결한 경우에만 별도의 승인 상태로 다음 단계로 넘긴다.
7. CLI/SDK 결과에는 처리 버전, 원본 추적 정보, 작업 상태, 검토 가능 근거를 함께 제공한다.

### 1B. 수용 시나리오
- 서로 다른 날짜/금액 표기를 포함한 CSV를 동일 스키마로 변환하면서 잘못된 행의 검토 이유를 보존한다.
- 일부 열 이름이 다르거나 비슷한 경우 후보를 표시하지만 승인 전에는 어떤 열도 임의로 매핑하지 않는다.
- 동일한 원본을 반복 처리하면 중복/원본 SHA/처리 버전으로 동일한 결과를 재검증할 수 있다.
- 결함 있는 입력과 접근 불가 경로에서는 입력 원본을 바꾸지 않고 예측 가능한 오류를 반환한다.
- 승인된 호스트 앱이 특정 배포 버전을 고정 참조한 상태에서 인터페이스 호환성 검증을 통과한다.

### 이번 v1.0에서 제외 또는 별도 제안
- PDF/DOCX/OCR, 비정형 문서 RAG 파이프라인, 이미지 전처리, 임의 SQL 실행, ERP/MES 쓰기, 결제/회원가입/원격 SaaS, AI의 무승인 자동 결정은 **v1.0 범위 밖**.
- XLSX, JSONL, 대용량 스트리밍, Python 래퍼, 통계적 결측치 추정, LLM 열 의미 해석 등은 **추가 범위로 제안 가능**. 별도 승인과 기능·성능 검증 없이는 기존 100% 기준에 끼워 넣거나 완료로 주장하지 않는다.
- 독립 웹 UI는 필수 요구가 아니다. HTML 정적 보고서는 선택 출력이다. UX 요구가 커지면 별도 제품/어댑터에서 검토한다.

## 3. 데이터 흐름·상태 전이
```text
User/Host permission
    ↓
Explicit local input + schema/config
    ↓
IO guard → parser → structural preflight
    ↓
Mapping suggestions (never applied automatically)
    ↓ [explicit mapping confirmed]
Deterministic normalization + quality checks
    ↓
Lineage / SHA-256 / reason-coded review queue
    ├─ INVALID / UNAVAILABLE → no output side-effect; actionable safe errors
    ├─ REVIEW_REQUIRED → preview and review receipt; downstream execution blocked
    └─ OK_FOR_OWNER_REVIEW → preview; still NOT_GRANTED
    ↓ [explicit export request]
Separate new local output files + verification receipt
    ↓
Pinned-version host adapter (business permissions owned by host)
```

**읽기 / 저장 / 승인 구분**: 검사·미리보기는 원본 읽기 전용, 결과 저장은 별도 명령, 그 결과를 기반으로 업무 실행할 권한은 PREP가 발급하지 않는다. 입력과 출력, 데이터 검토와 업무 승인을 같은 플래그로 취급하지 않는다.

## 4. 인터페이스(최종 계약은 구현 후 동결)
아래는 **예시 목표 API**이며 현재 제공되는 명령이 아니다.

- SDK: `inspectSource(input, options)`, `prepareDataset(input, explicitSchema, options)`, `verifyReceipt(result, source)`
- CLI: `prep inspect --input source.csv`, `prep run --input source.csv --config map.json --output prepared.json`, `prep verify --source source.csv --receipt receipt.json`
- 공통 결과: `schema_version`, `source_sha256`, `input_rows`, `output_rows`, `review_rows`, `review_queue`, `approval: NOT_GRANTED`, `execution: NOT_PERFORMED`, `transform_version`
- 상태: `OK_FOR_OWNER_REVIEW` / `REVIEW_REQUIRED` / `INVALID` / `UNAVAILABLE`. 소비자 앱에서 반드시 모든 상태를 분기 처리.
- 파괴적 스키마 변경은 새로운 주요 버전으로만 허용. **CLI 메시지·반환값·파일 포맷의 공식 사양은 골든 테스트 후 동결**.
- PREP 출력물에 원본 내용이 포함될 수 있으므로 영수증/메타데이터와 원본 행의 로깅·수집을 분리한다.

## 5. 보안·장애 복구·비용·중복 실행
- 모든 파일은 불신 입력이다. 경로 탈출, 특수 파일, 심볼릭 링크, 실행 가능한 셀 수식, 과대 입력, 비정상 인코딩, 헤더 중복, JSON 과도한 중첩을 테스트한다.
- 읽기 중 원본 변경 가능성을 검토하고, 입력 바이트 해시/영수증과 파일 불변 검증을 계약에 포함한다.
- 출력은 명시된 새 파일로만 생성; 임시 파일 사용·원자적 확정·오류 시 정리/복구를 요구한다.
- 동일 설정/입력 재실행은 결정론적 결과를 내고, 기존 경로의 자동 덮어쓰기나 결제를 트리거하지 않는다.
- 모든 예외는 상태와 검토 가능한 오류 코드로 표시하되 민감한 행·경로 전체를 기본 로그에 출력하지 않는다.
- 기본 배포는 오프라인, 필수 외부 호출 0회, 필수 유료 LLM/API 비용 0원. 별도 AI 어댑터는 승인·비용 상한·전송 근거를 갖춰야 한다.

## 6. 성능과 호환성 수용 목표 (실측 전 제안값)
- Node.js 20+ ESM, Linux와 Windows 10/11 로컬 실행/설치 검증.
- 초기 안정성 기준은 **최대 2 MiB CSV, 최대 20,000행, 최대 64개 매핑 필드**를 후보 한도로 삼고, 정확한 한도·메모리·시간은 베이스라인 측정 후 확정한다. 이 수치를 달성했다는 뜻이 아니다.
- 테스트는 최대치 직전/경계/초과 사례, 스트레스 및 회귀 기준을 포함한다.
- 무조건적 대용량 지원을 약속하지 않으며 더 큰 입력은 안전 거부 또는 별도 승인된 스트리밍 모듈로 분리한다.
- 포맷별 동작, 64비트 정수/고정소수점 정책, 날짜 시간대·정규화/로케일 정책을 공개 계약으로 문서화한다.
- 설치/실행은 사용자가 허용한 디렉터리에서 독립적으로 가능해야 한다. 특정 호스트 앱 실행을 필수로 하지 않는다.

## 7. 타 제품 연동 계약
- PREP는 **범용 엔진**이고 업무 판단은 소비자가 담당한다.
- 우선 연결 대상은 기존 데이터 표준화/자동화 앱 중 사용자가 승인한 한 제품이다. 다른 사내 앱, AI 분석/RAG/AutoML 등은 후속 플러그인 후보.
- 소비자는 PREP의 **고정 릴리스/패키지 버전**을 설치한다. GitHub 브랜치 최신 HEAD 직접 참조는 출시 의존성으로 쓰지 않는다.
- 소비자는 REVIEW_REQUIRED를 매출 확정·DB 반영·업무 실행 승인으로 해석할 수 없다.
- 원본 프로젝트의 현재 정상 로직 및 데이터는 유지하고, 어댑터를 별도로 두어 회귀 실패 시 기존 경로로 복구할 수 있어야 한다.

## 8. 최종 사용자에게 제공할 산출물
1. 실행 가능한 버전 고정 PREP 로컬 CLI와 라이브러리 패키지.
2. 샘플 합성 CSV/JSON, 명시 스키마 설정 예제, 설치·사용·오류 복구 설명서.
3. 타입/품질·검토 큐·근거·수치가 있는 JSON/CSV 결과물 및 안전한 HTML 리포트 예시.
4. 공개 API·상태/오류 코드·스키마 버전·변경 이력·어댑터 작성 문서.
5. SHA가 기록된 통합/보안/OS/패키지 검증 증거와 최소 한 개의 승인된 소비자 앱 연동 사례.
6. 라이선스·서드파티 의존성·개인정보/저장 위치·지원 범위·복구 방법.

## 9. 개발·완성률 판정 원칙
- `50%`: 독립 코어 실행, 원본 동등성/골든 테스트, 기본 안전성.
- `70%`: CSV·JSON·스키마·품질·검토 큐·CLI·입출력 경계 통합.
- `85%`: SDK/CLI 계약, 리포트·증거·보안/CI Linux 전체 검증.
- `95%`: Windows 원생 실행, 설치/패키지, 승인된 소비자 앱 1곳 E2E 검증.
- `100%`: R01~R12 전부 합격, 실패/복구/보안/권리 검수, 사용자 최종 승인.

**규칙:** 단계 기준에 부합하지 않으면 숫자를 올리지 않는다. 단계 완성률은 개발 진행 정도의 가설적 분류이며, 실구현 증거 없이 숫자 산출 금지. 상세 테스트와 합격 조건은 `docs/ACCEPTANCE_MATRIX.md`가 기준.

## 10. 사용자 확인 필요 사안
- 독립 GUI 여부, 초기 업로드 지원 형식, XLSX를 v1 필수로 올릴지 여부는 **현행 범위 밖 제안**으로 유지.
- PREP 저장소 현재 상태가 PUBLIC이면 비공개 원본 소스 이관 금지. 사용자 승인 없이 visibility 변경하지 않는다.
- 실제 고객 데이터, 외부 AI/유료 API, 개인정보 처리, 배포/라이선스 공개 등은 별도 승인.
- 100%는 상용 검증/권리/배포를 포함한 합격 판정이며, 달성했다고 보고하기 전 명시적 최종 검수 필요.

## 11. 최종 설계 변경 관리
`REQUIREMENTS.md`가 기능 ID 및 최소 합격 범위의 정본이다. 이 문서는 제품 관점의 전체 설계 정본이고, `docs/ARCHITECTURE.md`는 모듈 구조, `docs/ACCEPTANCE_MATRIX.md`는 검수 증거, `STATUS.md`는 실제 진행을 기록한다. 의견/추정·확정 범위가 다르면 이 문서와 승인 로그의 차이를 명시하고 사용자 승인 후 수정한다.
